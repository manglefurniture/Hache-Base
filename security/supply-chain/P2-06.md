# P2-06 — SBOM, provenance y referencias inmutables

P2-06 agrega una capa reusable de evidencia de supply chain para proyectos Hache **Nivel C** sin convertir Hache Base en una autoridad de firma ni afirmar un nivel SLSA que no existe.

## Alcance

Esta capa cubre tres cosas:

1. referencias inmutables de GitHub Actions y contenedores usados por workflows;
2. SBOM CycloneDX 1.6 derivada de lockfiles soportados del árbol versionado de `HEAD`;
3. provenance de enlace entre commit, artifact, CI/test evidence, materiales de workflow y SBOM.

No reemplaza P0-12. El baseline P0 sigue cubriendo lockfiles, secret scan, SCA, licencias y accepted risk; P2-06 utiliza esos mismos principios de evidencia atribuible al commit y añade identidad de build/materiales.

## Referencias inmutables

Ejemplos admitidos:

```yaml
- uses: actions/checkout@11d5960a326750d5838078e36cf38b85af677262 # v4

services:
  mariadb:
    image: mariadb:11.8@sha256:2439dcd7d14010ecd1ff7a4e1c5abe8e208c34fe35290744deeeaac3569043c3
```

Para Level C:

- una Action externa debe usar un commit SHA completo de 40 caracteres;
- `docker://...` debe usar digest `sha256`;
- `services.*.image` y `container.image` deben quedar fijados por digest;
- Actions locales `./...` son válidas porque su contenido queda ligado al commit del repo;
- imágenes dinámicas `${{ ... }}` no pueden contarse como evidencia inmutable por este checker.

Validación:

```bash
node tools/supply-chain/p2-evidence.mjs verify-workflows .
```

El checker lee los workflows **desde el árbol de `HEAD`**, no desde un working tree sucio.

### Frontera del parser de workflows

El checker no pretende ser un parser YAML general. Implementa un subconjunto conservador para las estructuras que afectan esta evidencia y **falla cerrado** cuando no puede demostrar cobertura completa.

En particular:

- reconoce `uses:` en estilo de bloque y también en pasos flow-style como `- { uses: ... }`;
- valida `image` únicamente cuando corresponde a `jobs.*.container` o `jobs.*.services.*.image`;
- una entrada normal de una Action llamada `image`, por ejemplo `with: { image: ./docs/logo.png }`, no se confunde con un contenedor;
- ignora texto dentro de block scalars de shell (`run: |` / `run: >-`) para que cadenas como `uses:` o `image:` en scripts no se interpreten como configuración;
- mappings completos de un job en flow-style se rechazan como no demostrables por este checker, en vez de otorgar un falso PASS;
- tabulaciones en la indentación se rechazan para evitar una interpretación ambigua del árbol.

Si un proyecto necesita sintaxis YAML fuera de esta frontera, debe extender el parser con regresiones equivalentes o usar un parser YAML versionado/lockeado antes de declarar la evidencia completa.

## SBOM

El comando `generate` produce `sbom.cdx.json` con formato CycloneDX 1.6.

La inventory de dependencias lee únicamente lockfiles versionados en `HEAD`:

- npm: `package-lock.json` / `npm-shrinkwrap.json`, lockfileVersion 2 o 3;
- Composer: `composer.lock`.

`yarn.lock` y `pnpm-lock.yaml` no se elevan silenciosamente a cobertura completa: el SBOM registra `PARTIAL_UNSUPPORTED_LOCKFILES`. Si no hay lockfiles soportados, registra `NO_SUPPORTED_LOCKFILES_FOUND`.

El SBOM identifica el artifact principal por el SHA-256 del manifest de artifact y lista las dependencias de lockfile como componentes. **No significa** que vulnerabilidades o licencias estén aprobadas; eso permanece en P0-12/SCA/licencias.

## Provenance

`provenance.json` usa el schema local:

```text
hache-release-provenance/v1
```

Enlaza:

- nombre, tamaño y SHA-256 del artifact real;
- repositorio y commit de origen;
- `ci_run_ref`, `build_evidence_ref` y `test_evidence_ref` ya presentes en `hache-artifact-manifest/v1`;
- referencias inmutables de Actions/containers de los workflows de `HEAD`;
- hash SHA-256 del SBOM generado.

La provenance declara además `materials_scope = VERSIONED_GITHUB_ACTIONS_AND_WORKFLOW_CONTAINERS_ONLY`, para no insinuar que enumera paquetes del runner, APT, imágenes implícitas u otros materiales fuera de los workflows versionados.

La decisión queda deliberadamente marcada como:

```text
UNSIGNED_PROVENANCE_LINKAGE_ONLY_NOT_SLSA_ATTESTATION
```

Es decir: demuestra enlace e identidad bajo este contrato, pero **no** afirma firma criptográfica, identidad de builder confiable ni cumplimiento SLSA.

## Generación

P2-06 se monta sobre el artifact/manifest ya generado por `deployment/build-artifact.sh`:

```bash
node tools/supply-chain/p2-evidence.mjs generate \
  --root /ruta/al/repo \
  --artifact-manifest /evidence/app.manifest.json \
  --artifact /evidence/app.tar.gz \
  --output-dir /evidence/p2-06 \
  --project mi-proyecto \
  --repository https://github.com/owner/repo
```

Antes de producir evidencia el comando vuelve a comprobar:

- que el manifest sea `hache-artifact-manifest/v1`;
- que sus campos de identidad/evidence existan;
- que `source_commit` coincida exactamente con `HEAD`;
- que nombre, tamaño y SHA-256 coincidan con **los bytes reales del artifact**;
- que los workflows del mismo `HEAD` no contengan referencias mutables o una sintaxis que el checker no pueda demostrar con seguridad.

Los archivos de salida se crean sin sobrescribir evidencia preexistente del mismo destino.

Así un manifest fabricado, un artifact cambiado después del build o una configuración de workflow no demostrable no pueden producir evidencia válida silenciosamente.

## Frontera de confianza

P2-06 no firma los JSON. Un proyecto que necesite attestations verificables por terceros debe añadir firma/identity provider/attestation store por encima de esta primitive y documentar esa capa en su threat model.

Tampoco se considera evidencia suficiente copiar un `sbom.cdx.json` o `provenance.json` viejo a otro build. El `source_commit` y el SHA-256 del artifact deben coincidir en cada generación.

## Evidencia mínima por proyecto Nivel C

Para declarar esta parte cubierta en un proyecto real conservar:

- SHA del commit liberado;
- artifact + `hache-artifact-manifest/v1` verificado;
- `sbom.cdx.json` del mismo commit/artifact;
- `provenance.json` del mismo commit/artifact;
- CI run donde pasó `verify-workflows`;
- evidencia de que sus workflows reales están fijados por SHA/digest;
- cobertura/limitaciones de lockfiles explícitas;
- revisión humana cuando el release requiera decisión Production Ready.

La existencia del tooling en Hache Base no convierte automáticamente SEC/ROB/OBS ni un proyecto derivado en PASS.
